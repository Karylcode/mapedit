## 一、必修

### F38. 估算的重疊會誤判，還會擋住人的修改（F32 的後續）

- **位置**：`packages/core/src/geometry.ts:296-299`、`:306`、`:322`；`packages/server/src/disk-state.ts:336`、`:405`；protocol.md 第 3 節（約 168 行）。
- **原因**：
  - **200 筆的上限連方塊和方塊的重疊也算進去。** 方塊重疊本來就不需要布林運算，算起來很便宜。結果只要地圖上已經有 200 筆方塊重疊，之後的非方塊模組就只能用外框估算。實測：兩座沒有碰到的圓柱塔，地圖上有 190 筆箱子重疊時沒事；箱子重疊變成 211 筆時，兩座塔就被報成「probably overlaps」。
  - **估算的重疊會擋住人的修改。** 預覽和套用時，被移動的東西只要有違規就拒絕。所以在有 200 筆以上重疊的地圖上，人沒辦法把非方塊的結構放到另一個結構旁邊，即使兩者根本沒碰到。
  - **措辭和文件太肯定。** 圓柱實測中，估算的重疊大約一半是假的，但訊息寫「probably overlaps」。protocol.md 說重新檢查一次就會得到精確結果，但其實要等前面的重疊少於 200 筆才會。
  - **估算的接觸也被當成支撐**（`:322`），可能把真的「沒有支撐」藏起來。這一點沒有寫在文件裡。
- **修法**：
  - 上限只計算真正需要布林運算的重疊，或直接計算布林運算的次數。
  - 預覽和套用時，被移動的東西所涉及的配對一律精確計算。
  - 訊息改成「may overlap」，並修正 protocol.md 的說明。前端的 FE26 會依 `params.estimated` 顯示「可能重疊」，兩邊的說法要一致。
  - 估算的接觸不要當成支撐；如果要保留，就寫進文件。
- **驗收**：上面的圓柱塔情境不會被報成重疊；在有 200 筆以上重疊的地圖上，可以把非方塊的結構放到另一個結構旁邊。

### F39. 修改紀錄沒有標出是哪張地圖

- **位置**：`packages/server/src/disk-state.ts:230`；protocol.md 的 `HistoryEntry`。
- **原因**：F35 替 notice 加上了 `mapId`，但修改紀錄還沒有。
  - 修改紀錄會送給每個連線，不管它打開的是哪張地圖。人的移動和刪除不會說明是在哪張地圖上做的。
  - Agent 改檔時，會把所有地圖的 `refs` 合在一起，兩張地圖上都叫 `structure:house` 的物件會重複出現，分不出來。
  - 前端會依照 `refs` 標出物件，所以可能標到另一張地圖上同 id 的東西。
- **修法**：
  - 人的修改加上選填的 `mapId`。
  - Agent 的修改依地圖分組列出 `refs`，例如 `maps: [{ mapId, refs }]`。
  - 只能新增欄位，舊欄位保留。先改 protocol.md，改完通知前端（前端的 FE30 在等這一項）。
- **驗收**：Agent 同時改兩張地圖時，修改紀錄能分出每張地圖的物件。

### F40. 錯誤處理的邊角情況

- **刪掉的地圖還留在快取裡**（`disk-state.ts:247`、`:260`）：
  - 地圖被打開過之後，即使 Agent 刪掉它，`getScene` 還是會回傳快取。其他分頁 `openMap` 時，收到的是一份帶著「does not exist」檔案錯誤的快照，而不是 `unknown_map`，和 protocol.md 第 4 節流程 2 的例子（「例如 Agent 剛刪掉它」）矛盾。
  - 之後每次有變動，還會一直重建這張地圖。
  - 修法：地圖不存在時，從快取移除，`openMap` 回 `unknown_map`。
- **重建失敗時，修改紀錄沒有送出**（`index.ts:330-336`）：
  - 套用、復原或重做成功之後，如果重建某一張打開中地圖的快照失敗，只會送 `file_error`。`history` 和其他地圖的快照都不會送，前端會一直顯示舊的修改紀錄。
  - 修法：單一張地圖失敗，不影響其他快照和 `history` 的廣播。
- **錯誤訊息帶有絕對路徑**（`index.ts:340`）：`internal_error` 的 `reason` 會直接帶出 Node 的錯誤，例如 `EBUSY … open 'C:\Users\…\houses.yaml'`。其他地方都用專案內的相對路徑，這裡也改成相對路徑。
- **前端建置只在啟動時找一次**（`index.ts:139`、`:376`，以及 CLI 的 `editorWebRoot`）：先執行 `mapedit dev` 再 `pnpm build` 的話，截圖會一直說「run pnpm build」，直到重新啟動。改成每次截圖時重新確認。
- **驗收**：每一點都有測試。

### F41. 截圖的總時間要短於 Agent 端的等待上限

- **位置**：`packages/server/src/screenshot.ts`。
- **原因**：載入頁面、等待 `mapeditRenderReady`、算繪分別最多 30、30、60 秒，一次截圖最長可能要 120 秒。MCP SDK 預設的請求逾時是 60 秒，Agent 那邊會先放棄，收不到後端說明原因的錯誤訊息。另外，頁面載入和等待 ready 的錯誤訊息沒有限制長度。
- **修法**：
  - 整次截圖設一個總時間上限，例如 50 秒，三個階段共用。
  - 所有錯誤訊息都限制長度。
- **驗收**：用永遠不會 ready 的假頁面測試，50 秒內回錯誤。

### F42. 人的修改寫到一半失敗時，檔案會留在半套用的狀態

- **位置**：`packages/server/src/disk-state.ts:424`、`:454`（`apply` 和 `travel`）。
- **原因**：
  - 一次修改可能要寫好幾個檔案。開始寫之後才失敗的話（例如 Windows 上 Agent 正在寫同一個檔案，出現 EBUSY），會留下寫了一半的檔案。
  - 下一次重新整理會把這些檔案當成 Agent 的修改記錄下來，還會清掉可以重做的紀錄。
  - protocol.md 流程 10 建議前端「稍後重試」，但這時候重試的前提已經不成立。這個問題在 F30 之前就有。
- **修法**：先把所有檔案寫到暫存檔，全部成功之後再一次替換；替換中途失敗，就還原已經替換的檔案。
- **驗收**：模擬第二個檔案寫入失敗，所有檔案都維持原樣，修改紀錄也不變。

## 二、建議

### F43. 整個結構旋轉後，緊貼的模組還是要做布林運算

- **原因**：互相緊貼、沒有重疊的模組不會被略過（`SKIP_GAP` 要分開超過 1e-7 才會略過），所以結構旋轉之後，每一對緊貼的模組都要做布林運算。這在 F32 之前就有，不是這一輪改出來的。2,000 個緊貼的模組、整個結構轉 30 度、完全沒有違規時的實測：

  | 模組 | 時間 |
  |---|---|
  | 方塊 | 0.77 秒 |
  | 有門洞的方塊 | 1.5 秒 |
  | 32 邊的圓柱 | 1.7 秒 |
  | 64 邊的圓柱 | 3.9 秒 |

- **修法**：精確計算之前，先用旋轉後的方塊做便宜的分離測試，緊貼但沒有重疊的配對直接略過。
- **驗收**：上面四種情況都在 2 秒內完成。
